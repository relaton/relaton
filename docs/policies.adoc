= Owner policy ledger

The standing rulings that govern how this repository is maintained. Each
entry names the issue or incident that raised the question and the ruling
that settles it; the governing details live where they are enforced
(generally the root CLAUDE.md). New policies append here — an entry is
amended only by a new dated ruling.

== P-001 Cassette re-recording is deliberate, never scheduled

Raised by #380 (follow-up to #360).

No suite re-records a VCR cassette by itself, now or on a schedule. Every
VCR config carries `re_record_interval: nil`, and
`spec/relaton/vcr_policy_spec.rb` fails on any other value, so a copied
config cannot reintroduce silent re-recording.

*CI is hermetic by design.* A scheduled re-record job is declined, and
these are the reasons the decline rests on:

- The publisher-format drift the old 7-day interval used to surface is
  now caught by deliberate signals instead: the daily contract alarm
  against api.relaton.org (relaton-api-js `contract.yml`) pins the API
  surface, and the relaton-data-* crawlers fail loudly when an upstream
  page no longer parses — drift reaches this repo as a crawler failure or
  a dataset update, not as a silently rewritten cassette.
- The operational constraints that made scheduled re-recording unsafe
  have not gone away: Crossref caps clients at 10 req/s with 3
  concurrent connections; ITU's WAF answers a whole-suite `/rec` burst
  with HTTP 500 and needs one-example-at-a-time re-records with pauses;
  CI runners cannot reach `openstd.samr.gov.cn` at all; a recorded
  429/5xx is a dead recording that must never be committed; and a
  cassette refresh is only half the reconciliation — the expected-XML
  fixtures move with it and need a person reading the diff.

*How drift is handled instead:* when a publisher moves, re-record
deliberately — delete the cassette, re-run that suite alone (never under
the parallel `rake spec`), reconcile the fixtures in the same commit, and
justify every hunk. The full procedure is the Testing section of the
root CLAUDE.md.

== P-002 Upstream feeds may carry duplicate JSON keys; the boundary absorbs it

Raised by #413.

Third-party feeds (NIST's pubs-export, Crossref works, the UN search API)
are generated by their publishers and sometimes repeat an object key.
json 3 / yeptris reject duplicates by default, so the boundary where this
repository parses an external payload — `Relaton::Core::Json.parse_external`
— opts into the historical last-wins contract
(`allow_duplicate_key: true`). Everything this repository *writes* —
fixtures, cassettes, datasets — parses under strict
`allow_duplicate_key: false`, and a duplicate found in a committed
fixture is adopted-data damage to fix, never a reason to widen the
strictness elsewhere.

We cannot file against these publishers; when a feed's duplicates start
breaking the lenient boundary too, the answer is a stricter local
normalization of that feed, reported here.
